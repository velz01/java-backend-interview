# Индексы и EXPLAIN

::: tip Приоритет
🔴 **Очень частая тема.**
:::

## Что такое индекс?

Дополнительная структура данных, которая ускоряет поиск подходящих rows, но требует места и обслуживания на INSERT/UPDATE/DELETE.

## Почему индекс не всегда используется?

Если query читает большую долю table, Seq Scan может быть дешевле. Также predicate может не соответствовать index, statistics могут быть неточными, expression может мешать обычному index.

## B-tree

Универсальный ordered index для equality/range/sort/prefix composite index.

## Hash index

Ориентирован на equality lookups. В PostgreSQL обычно B-tree остаётся default, если нет специфической причины.

## Composite index

Порядок columns важен. Индекс `(a,b)` особенно полезен, когда query ограничивает leading column `a`; не эквивалентен отдельному index по `b`.

## Selectivity

Насколько condition сокращает число rows. Низкоселективное boolean поле часто мало помогает само по себе.

## Partial index

Индекс только по rows, удовлетворяющим predicate. Полезен, когда запросы часто работают с небольшим subset, например `status='ACTIVE'`.

## Expression index

Индекс на выражение, например `lower(email)`, если queries действительно используют то же выражение.

## Covering / INCLUDE

Можно добавить non-key columns, чтобы query получил нужные данные из index и потенциально использовал index-only scan.

## Index-only scan

БД может получить values из index без heap access для каждой row, если visibility map позволяет.

## EXPLAIN

Показывает plan и estimates.

## EXPLAIN ANALYZE

Реально выполняет query и показывает actual rows/timings. Осторожно с UPDATE/DELETE/INSERT на production.

## Cost

Это не миллисекунды, а относительная модель optimizer. Важнее сравнивать estimates и plan choices.

## Estimated rows vs actual rows

Большое расхождение часто указывает на плохую statistics/correlation и может привести к плохому join strategy.

## Seq Scan — всегда плохо?

Нет. Для маленькой table или запроса, читающего значительную часть rows, Seq Scan может быть лучшим plan.

## N+1 и индексы

Даже идеально индексированный query не спасёт, если приложение делает 1001 round-trip вместо одного/нескольких разумных запросов.

## Углубление для собеседования

### Почему B-tree подходит для диапазонов?

Ключи хранятся упорядоченно, поэтому дерево позволяет быстро найти начало диапазона и последовательно читать соседние записи. Hash index хорош для equality, но не решает range/order задачи так же естественно.

### Почему индекс ускоряет SELECT, но замедляет запись?

При INSERT/UPDATE/DELETE СУБД должна поддерживать не только таблицу, но и все затронутые индексные структуры. Чем больше индексов — тем больше I/O, памяти и работы vacuum/maintenance.

### Что такое составной индекс и почему важен порядок колонок?

Индекс `(a, b, c)` организован прежде всего по `a`, затем `b`, затем `c`. Условия по leading columns обычно использовать легче. Индекс только по `b` не всегда эффективно заменяется индексом `(a,b)`.

### Что такое селективность?

Насколько условие сокращает число строк. Индекс по колонке с двумя значениями на огромной таблице может быть мало полезен для запроса, возвращающего половину таблицы: sequential scan бывает дешевле.

### Почему PostgreSQL может не использовать индекс?

Планировщик оценивает стоимость. Причины: запрос возвращает большую долю таблицы, статистика считает seq scan дешевле, выражение мешает использовать обычный индекс, типы/касты не совпадают, маленькая таблица, устаревшая статистика.

### EXPLAIN vs EXPLAIN ANALYZE

`EXPLAIN` показывает план и оценки без выполнения запроса. `EXPLAIN ANALYZE` выполняет запрос и показывает фактические timings/rows. Для изменяющих запросов с ANALYZE нужно быть особенно осторожным — запрос действительно выполнится.

### Index Scan vs Index Only Scan

Index Scan находит ссылки через индекс и часто читает heap/table. Index Only Scan может вернуть нужные колонки из индекса, если visibility map позволяет подтвердить видимость без лишнего heap access.
