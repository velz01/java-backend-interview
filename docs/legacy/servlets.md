# Servlet API

Вопросы по Servlet API, жизненному циклу, фильтрам, сессиям и безопасности. Раздел полезен для понимания основы Java Web и старых проектов.

## 1. Что такое сервлет?

> 🔴 **Обязательно знать**

Servlet — Java-компонент, работающий под управлением servlet container и обрабатывающий запросы клиентов. Для HTTP обычно наследуются от HttpServlet: контейнер создаёт экземпляр, управляет его жизненным циклом и вызывает service(), который маршрутизирует запрос к doGet(), doPost() и другим методам.

---

## 2. Что такое контейнер сервлетов?

> 🔴 **Обязательно знать**

Servlet container — среда выполнения Servlet API. Он принимает сетевые HTTP-запросы, сопоставляет URL сервлетам и фильтрам, создаёт ServletRequest/ServletResponse, управляет жизненным циклом компонентов, потоками, сессиями и частью механизмов безопасности. Примеры — Tomcat и Jetty.

---

## 3. Как контейнер управляет жизненным циклом servlet?

> 🔴 **Обязательно знать**

Контейнер загружает класс, создаёт экземпляр и один раз вызывает init(). Затем для каждого запроса вызывает service(); у HttpServlet service() выбирает doGet/doPost/doPut/doDelete и т.д. Перед выгрузкой приложения контейнер один раз вызывает destroy(), после чего экземпляр становится кандидатом на сборку мусора.

---

## 4. Что такое servlet filters?

> 🔴 **Обязательно знать**

Filter перехватывает запрос и/или ответ до servlet и после него. Метод doFilter может проверить или изменить request/response, прекратить цепочку либо вызвать chain.doFilter() для продолжения. Фильтры используют для аутентификации, логирования, CORS, encoding, compression и общей обработки.

---

## 5. Когда использовать filter, а когда listener?

> 🔴 **Обязательно знать**

Filter участвует непосредственно в обработке каждого подходящего запроса/ответа и может менять или блокировать его. Listener ничего не маршрутизирует; он реагирует на событие контейнера — создание контекста, сессии, request или изменение атрибута.

Поэтому авторизация запроса — filter, инициализация ресурса при старте приложения — listener.

---

## 6. Для чего нужен ServletResponse?

> 🔴 **Обязательно знать**

ServletResponse представляет ответ клиенту. Он позволяет настроить content type, encoding, buffer и получить Writer или OutputStream для тела. В HTTP обычно используется HttpServletResponse, который добавляет status codes, headers, cookies и redirect.

---

## 7. Для чего нужен ServletRequest?

> 🔴 **Обязательно знать**

ServletRequest представляет входящий запрос: параметры, attributes, body stream/reader, локаль и сведения о соединении. HttpServletRequest добавляет HTTP-specific данные — method, URI, headers, cookies, session и principal.

---

## 8. Что такое RequestDispatcher?

> 🔴 **Обязательно знать**

RequestDispatcher позволяет передать обработку запроса другому ресурсу внутри того же server-side приложения через forward() или включить результат другого ресурса через include(). При forward браузер не выполняет новый запрос и URL в адресной строке не меняется.

---

## 9. Что такое attributes servlet request/session/context?

> 🔴 **Обязательно знать**

Attribute — объект, сохранённый под именем через setAttribute/getAttribute. Request attributes живут только в пределах запроса и удобны для передачи данных между компонентами при forward. Session attributes связаны с пользовательской сессией, context attributes — со всем web-приложением и требуют особого внимания к потокобезопасности.

---

## 10. Какие способы управления session существуют?

> 🔴 **Обязательно знать**

Основной механизм — cookie JSESSIONID. Если cookies недоступны, Servlet API поддерживает URL rewriting, добавляя идентификатор сессии к URL. Сессия представлена HttpSession; её можно получить через request.getSession(), инвалидировать invalidate() и настроить timeout.

---

## 11. Что такое HttpSession?

> 🔴 **Обязательно знать**

HttpSession хранит server-side состояние пользователя между запросами. Сессия имеет id, время создания/последнего доступа, timeout и набор attributes. getSession(true) создаёт сессию при отсутствии, getSession(false) возвращает null. invalidate() завершает её.

---

## 12. Как объект узнаёт, что его удалили из session или session уничтожена?

> 🔴 **Обязательно знать**

Для реакции объекта-attribute используется HttpSessionBindingListener с valueBound/valueUnbound. События создания и уничтожения самих sessions отслеживаются HttpSessionListener. Для изменения attributes есть HttpSessionAttributeListener.

---

## 13. Как ограничить доступ servlet только пользователям с валидной session?

> 🔴 **Обязательно знать**

Централизованный вариант — Filter, сопоставленный защищённым URL: он проверяет наличие session/identity и либо передаёт запрос дальше, либо возвращает ошибку/redirect. Ещё лучше использовать container security или framework security, чтобы политика не дублировалась в каждом servlet.

---

## 14. Что такое cookies в Servlet API?

> 🟡 **Часто спрашивают**

Cookie — name/value с атрибутами, которое сервер добавляет в response, а браузер возвращает в следующих запросах. Servlet API предоставляет Cookie и HttpServletResponse.addCookie(); входящие cookies доступны через HttpServletRequest.getCookies().

---

## 15. Какие операции с Cookie доступны?

> 🟡 **Часто спрашивают**

Можно задать name/value, max age, path, domain, secure, HttpOnly и другие параметры в зависимости от версии Servlet API. Для удаления сервер обычно отправляет cookie с тем же name/path и Max-Age=0. Современные security-настройки SameSite иногда задаются через header или новые API версии контейнера.

---

## 16. В чем преимущества сервлетов перед CGI?

> ⚪ **Дополнительно**

CGI часто запускает отдельный процесс для каждого запроса, что создаёт большие накладные расходы. Servlet живёт внутри процесса JVM и обычно один экземпляр обслуживает много запросов разными потоками. Контейнер также предоставляет управление жизненным циклом, сессиями, безопасностью, ресурсами и конфигурацией.

---

## 17. Какова типичная структура Java web-проекта?

> ⚪ **Дополнительно**

Классическая WAR-структура содержит публичные ресурсы приложения и каталог WEB-INF. В WEB-INF лежат web.xml, классы и библиотеки в WEB-INF/classes и WEB-INF/lib; содержимое WEB-INF нельзя запросить напрямую через браузер. Современные build tools формируют эту структуру автоматически, а embedded-container приложения часто запускаются без ручной сборки WAR.

---

## 18. Зачем нужны application servers, если есть servlet containers?

> ⚪ **Дополнительно**

Servlet container реализует прежде всего Web/Servlet-спецификации. Полноценный Jakarta EE application server может дополнительно предоставлять JPA, JTA, JMS, CDI, EJB и другие сервисы платформы. Если приложение использует только Servlet/Spring-стек, отдельный полный application server часто не нужен.

---

## 19. Что такое deployment descriptor?

> ⚪ **Дополнительно**

Deployment descriptor — файл WEB-INF/web.xml, в котором традиционно настраивались servlet, filter, listener, URL mappings, error pages, security constraints, session settings и другие параметры web-приложения. Начиная с Servlet 3 многие настройки могут задаваться аннотациями и программно, поэтому web.xml может быть минимальным или отсутствовать.

---

## 20. Что нужно сделать, чтобы создать servlet?

> ⚪ **Дополнительно**

Создать класс, обычно наследующий HttpServlet, реализовать нужные doXxx методы и сопоставить servlet с URL через @WebServlet либо web.xml. Приложение должно быть развернуто в совместимом контейнере. В современных фреймворках прямое создание servlet часто скрыто за DispatcherServlet и контроллерами.

---

## 21. Когда имеет смысл переопределять service()?

> ⚪ **Дополнительно**

У HttpServlet обычно переопределяют doGet/doPost и другие методы, потому что service() уже определяет HTTP method и делегирует. Переопределение service() оправдано, только если нужен общий низкоуровневый контроль обработки всех HTTP-методов; при этом легко сломать стандартную маршрутизацию, поэтому это редкий сценарий.

---

## 22. Нужно ли определять конструктор servlet и где инициализировать данные?

> ⚪ **Дополнительно**

Обычный Java-конструктор возможен, но в нём ещё недоступны ServletConfig и ServletContext, которые контейнер передаёт позже. Инициализацию, зависящую от окружения servlet, следует выполнять в init(). Ресурсы уровня приложения лучше получать через контейнер/DI и освобождать в соответствующем lifecycle.

---

## 23. Почему при переопределении init лучше использовать init() без аргументов?

> ⚪ **Дополнительно**

GenericServlet реализует init(ServletConfig): сохраняет конфигурацию, а затем вызывает init() без аргументов. Если наследник переопределяет именно init(), стандартная логика сохранения ServletConfig остаётся intact. При переопределении init(ServletConfig) нужно самостоятельно вызвать super.init(config), иначе часть механизма GenericServlet будет потеряна.

---

## 24. Какие задачи выполняет servlet container?

> ⚪ **Дополнительно**

Контейнер управляет загрузкой и жизненным циклом servlet, создаёт request/response, распределяет запросы по потокам, выполняет URL mapping, фильтры и listeners, управляет HTTP sessions, security constraints, error pages, ресурсами приложения и интеграцией с сетевым сервером.

---

## 25. Зачем нужны listeners в Servlet API?

> ⚪ **Дополнительно**

Listener реагирует на события жизненного цикла web-приложения, сессий, request и атрибутов. Например ServletContextListener получает уведомления о старте/остановке приложения, HttpSessionListener — о создании/уничтожении сессий. Это удобно для инициализации общих ресурсов и наблюдения за событиями.

---

## 26. Как запустить servlet при старте приложения?

> ⚪ **Дополнительно**

В web.xml используют load-on-startup либо атрибут loadOnStartup у @WebServlet. Тогда контейнер создаёт и инициализирует servlet при развертывании, а не при первом обращении. Порядок может определяться числовым значением.

---

## 27. Как обрабатывать ошибки servlet на уровне приложения?

> ⚪ **Дополнительно**

В web.xml можно настроить error-page для status code или exception type. Контейнер перенаправит обработку на заданный ресурс с атрибутами ошибки в request. В Spring MVC аналогичную высокоуровневую задачу часто решают @ExceptionHandler и @ControllerAdvice, но это уже поверх Servlet API.

---

## 28. Что такое ServletConfig?

> ⚪ **Дополнительно**

ServletConfig — конфигурация конкретного экземпляра servlet. Через него доступны init parameters этого servlet и ServletContext. Объект создаёт контейнер и передаёт в init(ServletConfig).

---

## 29. Что такое ServletContext?

> ⚪ **Дополнительно**

ServletContext представляет web-приложение целиком и является общим для всех его servlet. Через него получают общие init parameters, ресурсы, атрибуты приложения, информацию о контейнере и средства диспетчеризации запросов. Атрибуты context разделяются между потоками, поэтому доступ к изменяемым объектам должен быть безопасным.

---

## 30. Чем ServletContext отличается от ServletConfig?

> ⚪ **Дополнительно**

ServletConfig относится к одному servlet и хранит его параметры. ServletContext относится ко всему web-приложению и используется всеми servlet/filter/listener этого приложения. Из ServletConfig можно получить ServletContext.

---

## 31. Как из одного servlet вызвать другой?

> ⚪ **Дополнительно**

Обычно получают RequestDispatcher по path или name и вызывают forward() либо include(). Это серверная передача в рамках текущего request. Альтернатива — sendRedirect(), но тогда клиент выполняет новый HTTP-запрос.

---

## 32. Чем sendRedirect() отличается от forward()?

> ⚪ **Дополнительно**

forward() выполняется внутри контейнера в рамках того же request/response; браузер не знает о передаче и URL не меняется. sendRedirect() отправляет клиенту 3xx с Location, после чего браузер создаёт новый запрос; URL меняется, request attributes не сохраняются автоматически, зато можно перенаправить на внешний адрес.

---

## 33. Как в servlet можно получить deadlock?

> ⚪ **Дополнительно**

Так же, как в любом многопоточном Java-коде: два request thread могут захватить общие locks в разном порядке и ждать друг друга. Особенно опасно синхронизироваться на общих session/context объектах или держать lock во время внешнего IO.

Servlet по умолчанию обслуживается несколькими потоками, поэтому shared mutable state требует обычной concurrency-дисциплины.

---

## 34. Как получить реальный путь ресурса web-приложения?

> ⚪ **Дополнительно**

ServletContext.getRealPath(path) может вернуть файловый путь к ресурсу, если контейнер разворачивает приложение в файловую систему. Но это не гарантируется, например для нераспакованного WAR. Для portable-кода лучше использовать getResource()/getResourceAsStream().

---

## 35. Как получить информацию о servlet container?

> ⚪ **Дополнительно**

ServletContext предоставляет getServerInfo(), getMajorVersion()/getMinorVersion() и другие методы. Через request также можно получить scheme, serverName, serverPort, protocol и сведения о клиентском соединении.

---

## 36. Как получить IP клиента?

> ⚪ **Дополнительно**

HttpServletRequest.getRemoteAddr() возвращает адрес непосредственного peer. Если приложение стоит за reverse proxy/load balancer, это может быть адрес прокси; реальный client IP передаётся в доверенных proxy headers вроде X-Forwarded-For или Forwarded.

Такие headers нельзя слепо принимать от внешнего клиента — граница доверия должна быть настроена инфраструктурой.

---

## 37. Какие wrapper-классы есть в Servlet API?

> ⚪ **Дополнительно**

ServletRequestWrapper/HttpServletRequestWrapper и ServletResponseWrapper/HttpServletResponseWrapper делегируют исходному объекту и позволяют переопределить отдельные методы. Их часто используют фильтры для модификации headers, body или поведения request/response.

---

## 38. Чем GenericServlet отличается от HttpServlet?

> ⚪ **Дополнительно**

GenericServlet — протокол-независимый абстрактный servlet, реализующий базовую lifecycle-инфраструктуру. HttpServlet наследуется от него и специализируется на HTTP, добавляя doGet(), doPost(), doPut(), doDelete(), doHead(), doOptions() и маршрутизацию по method.

---

## 39. Почему HttpServlet объявлен abstract?

> ⚪ **Дополнительно**

HttpServlet задаёт инфраструктуру и стандартную HTTP-маршрутизацию, но не знает бизнес-логики конкретного приложения. Наследник должен переопределить один или несколько doXxx методов. Технически не каждый абстрактный класс обязан содержать abstract method — модификатор запрещает бессмысленное прямое создание экземпляра базовой реализации.

---

## 40. Какие основные методы HttpServlet нужно знать?

> ⚪ **Дополнительно**

service() маршрутизирует запрос; doGet(), doPost(), doPut(), doDelete(), doHead(), doOptions(), doTrace() соответствуют HTTP methods. init() и destroy() наследуются из lifecycle Servlet. На практике чаще переопределяют doGet/doPost и не трогают service().

---

## 41. Нужно ли заботиться о потокобезопасности servlet?

> ⚪ **Дополнительно**

Да. Контейнер обычно создаёт один экземпляр servlet и вызывает его методы одновременно из многих request threads. Поэтому нельзя хранить изменяемое состояние конкретного запроса в полях servlet без синхронизации.

Локальные переменные метода принадлежат отдельному стеку потока и безопаснее для request-specific состояния.

---

## 42. Какие HTTP methods safe/idempotent и почему это важно для servlet?

> ⚪ **Дополнительно**

GET, HEAD, OPTIONS и TRACE определены как safe: они предназначены для чтения/диагностики без изменения целевого состояния. GET, HEAD, PUT, DELETE, OPTIONS и TRACE считаются idempotent. Реализация doGet не должна неожиданно выполнять бизнес-операцию изменения состояния только потому, что технически Java это позволяет.

---

## 43. Какими способами клиент передаёт данные servlet?

> ⚪ **Дополнительно**

Данные могут находиться в path/query parameters, headers, cookies и request body. Form data передаётся как application/x-www-form-urlencoded или multipart/form-data, API — часто JSON/XML. HttpServletRequest предоставляет методы для parameters/headers/cookies и Reader/InputStream для body.

---

## 44. В чем разница GET и POST в Servlet API?

> ⚪ **Дополнительно**

GET обрабатывается doGet и обычно используется для получения ресурса; его параметры часто находятся в URL. POST идёт в doPost и обычно содержит body с данными команды/создания ресурса. GET safe и idempotent по HTTP-семантике, POST такими свойствами не обладает автоматически.

---

## 45. Чем PrintWriter отличается от ServletOutputStream?

> ⚪ **Дополнительно**

PrintWriter предназначен для символьного текста и применяет character encoding response. ServletOutputStream пишет сырые bytes и нужен для бинарных данных. Оба получают из response и работают с одним body.

---

## 46. Можно ли одновременно использовать PrintWriter и ServletOutputStream?

> ⚪ **Дополнительно**

Нет, для одного response выбирают одно представление тела. После getWriter() вызов getOutputStream() и наоборот обычно приводит к IllegalStateException. Нужно заранее решить, формируется текстовый или бинарный ответ.

---

## 47. Что такое SingleThreadModel?

> ⚪ **Дополнительно**

SingleThreadModel был старым маркерным интерфейсом, который пытался гарантировать отсутствие одновременного выполнения service() одним экземпляром servlet. Он deprecated и удалён как плохое решение: shared state мог находиться в session/context/static и всё равно оставаться небезопасным.

Потокобезопасность следует проектировать явно.

---

## 48. Что такое URL encoding и как его выполнять?

> ⚪ **Дополнительно**

Percent-encoding кодирует в URI символы, которые нельзя или нежелательно передавать буквально, как %HH байты в заданной кодировке. Для form/query компонентов в Java существует URLEncoder/URLDecoder, но важно понимать, что они реализуют application/x-www-form-urlencoded semantics и не являются универсальным кодировщиком всего URL.

---

## 49. Что такое URL rewriting?

> ⚪ **Дополнительно**

URL rewriting для session tracking добавляет session id к URL, если клиент не использует cookies. Контейнер умеет делать это через response.encodeURL()/encodeRedirectURL(). Этот механизм менее удобен и может раскрывать идентификатор в URL, истории и логах, поэтому cookies обычно предпочтительнее.

---

## 50. Чем encodeURL() отличается от encodeRedirectURL()?

> ⚪ **Дополнительно**

Оба позволяют контейнеру при необходимости включить session id в URL. encodeURL используется для обычных ссылок внутри приложения, encodeRedirectURL — для URL, передаваемых в sendRedirect, где правила формирования могут отличаться.

---

## 51. Как обеспечить TLS для web-приложения?

> ⚪ **Дополнительно**

TLS обычно настраивается на servlet container или reverse proxy. В deployment descriptor можно потребовать confidential transport через security-constraint. В production сертификаты, cipher suites, TLS versions и перенаправление HTTP→HTTPS обычно управляются инфраструктурой.

---

## 52. Как организовывать DB connections и logging в servlet?

> ⚪ **Дополнительно**

Нельзя создавать тяжёлое соединение с БД на каждый вызов без пула и хранить один Connection в поле servlet. Обычно DataSource/connection pool создаётся на уровне приложения и Connection берётся на время операции. Logging выполняется общей logging framework, а logger обычно static final и потокобезопасен.

---

## 53. Что важного появилось в Servlet 3?

> ⚪ **Дополнительно**

Servlet 3 добавил annotation-based конфигурацию (@WebServlet/@WebFilter/@WebListener), программную регистрацию компонентов, pluggability через web fragments и ServletContainerInitializer, а также async processing. Это уменьшило обязательность большого web.xml и упростило фреймворкам автоконфигурацию.

---

## 54. Какие способы аутентификации поддерживает container security?

> ⚪ **Дополнительно**

Традиционно Servlet/Jakarta Security описывает BASIC, FORM, CLIENT-CERT и DIGEST (исторически) через deployment configuration. Современные приложения часто используют внешнюю Spring Security/OAuth2/OIDC инфраструктуру, но HttpServletRequest всё равно может предоставлять Principal и методы проверки ролей.
