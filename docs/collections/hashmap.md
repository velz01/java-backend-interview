# HashMap — полный разбор

::: tip Приоритет
🔴 **Must know.** Это одна из тем, по которой интервьюер легко задаёт 10–15 follow-up вопросов. Нужно понимать механику, а не только определение.
:::

## Что такое HashMap?

### Короткий ответ
`HashMap<K,V>` — реализация `Map`, построенная на хэш-таблице. По `hashCode()` ключа вычисляется хэш и выбирается bucket, а равенство ключа внутри bucket проверяется через `equals()`. В среднем `get/put/remove` работают за **O(1)**. Порядок элементов не гарантируется. Допускается один `null` key и несколько `null` values.

### Подробнее
Внутри находится массив ссылок на узлы. Узел хранит `hash`, `key`, `value` и ссылку `next`. Несколько ключей могут попасть в один bucket — это **коллизия**. В современных реализациях длинная цепочка при определённых условиях может быть преобразована в красно-чёрное дерево.

```text
 table
 ┌─────┐
 │  0  │ -> null
 ├─────┤
 │  1  │ -> Node(A) -> Node(B)
 ├─────┤
 │  2  │ -> Node(C)
 └─────┘
```

## Что такое bucket?

Bucket — позиция во внутреннем массиве HashMap. Это **не обязательно один элемент**: bucket может быть пустым, содержать один `Node`, цепочку `Node` или дерево `TreeNode`.

## Как из key получается bucket?

У ключа вызывается `hashCode()`, затем HashMap дополнительно смешивает старшие и младшие биты хэша. Индекс выбирается с учётом длины таблицы. Поскольку capacity — степень двойки, индекс можно эффективно вычислять битовой операцией вида `(n - 1) & hash`.

**На собеседовании достаточно уверенно объяснить цепочку:** `key → hashCode → внутренний hash → index bucket`.

## Зачем HashMap дополнительно преобразует hashCode()?

Чтобы старшие биты исходного `hashCode()` тоже влияли на индекс. Это снижает риск плохого распределения, особенно когда capacity относительно небольшая.

## Что такое коллизия?

Коллизия — ситуация, когда разные ключи попали в один bucket. Это нормальная часть работы хэш-таблицы. Одинаковый bucket или одинаковый hash ещё не означает равенство ключей: окончательно они сравниваются через `equals()`.

## Как работает put()?

### Короткий ответ
1. Вычисляется hash ключа.
2. Выбирается bucket.
3. Если bucket пуст — создаётся новый узел.
4. Если bucket занят — ищется существующий равный key.
5. Если key найден — заменяется value и `size` не растёт.
6. Если key новый — добавляется узел.
7. При превышении threshold может произойти resize.
8. При длинной цепочке и достаточно большой таблице возможна treeification.

### Что возвращает put()?
`put()` возвращает **предыдущее значение** по этому ключу или `null`, если mapping отсутствовал. Но если `null` был сохранён как значение, по одному результату `put/get` нельзя отличить «ключа нет» от «ключ есть, value=null» — для этого используется `containsKey()`.

## Как работает get()?

1. Вычисляет hash и bucket index.
2. Проверяет первый узел.
3. Для кандидата сначала сравнивается hash, затем key через `==`/`equals()` в логике реализации.
4. Если bucket — цепочка, выполняется проход по ней; если дерево — поиск по дереву.

## Почему нельзя определять ключ только по hashCode()?

Потому что разные объекты **могут иметь одинаковый hashCode**. Контракт гарантирует обратное направление: если объекты равны по `equals()`, их hashCode обязан быть одинаковым. Но одинаковый hashCode не гарантирует `equals()==true`.

## Какая сложность операций?

В среднем `get/put/remove` — **O(1)** при хорошем распределении ключей. В плохом случае большое число элементов оказывается в одном bucket. Цепочка даёт линейный поиск, дерево позволяет улучшить поведение длинного bucket примерно до O(log n).

::: warning Частая ошибка
Фраза «HashMap всегда O(1)» неправильная. O(1) — ожидаемая средняя сложность при нормальном распределении.
:::

## Что такое capacity, load factor и threshold?

- **capacity** — длина внутренней таблицы;
- **load factor** — коэффициент, определяющий допустимую заполненность; типичное значение `0.75`;
- **threshold** — значение `capacity × loadFactor`, после превышения которого таблица расширяется.

Load factor — компромисс между памятью и количеством коллизий. Слишком маленький — больше расход памяти; слишком большой — выше плотность bucket и риск ухудшения поиска.

## Что происходит при resize?

Таблица увеличивается, а элементы распределяются между новыми bucket. Resize значительно дороже обычного `put`, поэтому при заранее известном большом размере имеет смысл корректно выбирать initial capacity.

При удвоении capacity элемент во многих современных реализациях либо остаётся на прежнем индексе, либо перемещается на `oldIndex + oldCapacity`. Полный повторный modulo для каждого элемента не требуется.

## Что такое treeification?

Когда цепочка в bucket становится длинной, она может превратиться в красно-чёрное дерево. Это защищает от сильной деградации поиска при большом количестве коллизий.

Полезно помнить детали OpenJDK: ориентир — **8 элементов для treeification**, но дерево создаётся только при достаточно большой общей capacity (ориентир **64**). Если таблица маленькая, HashMap скорее увеличит её, чем сразу построит дерево.

## Что такое untreeify?

Если число элементов в tree bucket уменьшается, структура может вернуться к обычной цепочке. Дерево имеет больший memory overhead, поэтому для небольших bucket оно невыгодно.

## Что будет, если hashCode() всех ключей возвращает одно число?

HashMap логически продолжит работать, если `equals()` реализован корректно, но все ключи будут конкурировать в одном bucket. Производительность резко ухудшится: цель хэш-таблицы — распределять ключи по разным bucket.

## Почему mutable key опасен?

Если после `put` изменить поля ключа, которые участвуют в `equals/hashCode`, новый `get(key)` может вычислить другой hash и пойти в другой bucket. Entry физически остаётся там, куда её положили по старому состоянию ключа, и найти её обычным lookup становится невозможно.

```java
var key = new UserKey(10);
map.put(key, "value");
key.setId(20); // если id участвует в equals/hashCode — опасно
System.out.println(map.get(key)); // может вернуть null
```

Поэтому ключи HashMap желательно делать immutable.

## Почему String удобен как key?

`String` immutable, а `equals/hashCode` определены по содержимому. После вставки строка не изменит своё логическое состояние, поэтому bucket не «потеряется».

## Можно ли использовать null?

`HashMap` допускает **один `null` key** и любое число `null` values. `ConcurrentHashMap` не допускает ни `null` keys, ни `null` values.

## Почему ConcurrentHashMap запрещает null?

В конкурентной среде `get(key) == null` должно однозначно означать «mapping отсутствует». Если бы null-value разрешался, пришлось бы делать отдельный `containsKey()`, а между `get()` и `containsKey()` другой поток мог бы изменить map — результат стал бы неоднозначным.

## HashMap vs Hashtable

`Hashtable` — legacy-класс, его публичные операции синхронизированы, `null` не поддерживается. Для современной конкурентной работы обычно выбирают `ConcurrentHashMap`, а не `Hashtable`.

## HashMap vs ConcurrentHashMap

`HashMap` не thread-safe. `ConcurrentHashMap` позволяет конкурентные чтения и обновления с более тонкой координацией и атомарными операциями (`putIfAbsent`, `compute`, `merge`). Нельзя считать `Collections.synchronizedMap()` полноценным эквивалентом: там обычно грубее блокировка и другой набор atomic compound operations.

## HashMap vs TreeMap

| HashMap | TreeMap |
|---|---|
| Хэш-таблица | Красно-чёрное дерево |
| В среднем O(1) | O(log n) |
| Порядок не гарантирован | Ключи отсортированы |
| Нужны hashCode + equals | Нужен Comparable/Comparator |

## HashMap vs LinkedHashMap

`LinkedHashMap` дополнительно связывает entries в порядке вставки или доступа. Это удобно, когда нужен предсказуемый iteration order или LRU-подобное поведение.

## Почему порядок HashMap нельзя использовать как контракт?

Даже если на маленьком примере порядок кажется стабильным, API его не гарантирует. Он зависит от хэшей, capacity, resize и версии реализации. Если порядок важен — используй `LinkedHashMap` или `TreeMap`.

## Что произойдёт при put() существующего key?

Новый Node для логически того же key не добавляется. Value заменяется, размер Map не увеличивается, `put` возвращает старое value.

## containsKey() vs get(key) != null

Если `null` values разрешены, `get()==null` не говорит, отсутствует ли key. `containsKey()` отвечает именно на наличие mapping.

## Почему HashMap не thread-safe?

Внутренние изменения `table`, цепочек, `size`, resize выполняются без общего внешнего контракта синхронизации. Одновременные записи могут приводить к lost update и некорректному наблюдению состояния. Для shared mutable map между потоками нужен подходящий concurrent container или внешняя синхронизация.

## Что делает computeIfAbsent()?

Вычисляет value только если mapping отсутствует:

```java
Map<Long, List<Order>> byUser = new HashMap<>();
byUser.computeIfAbsent(userId, id -> new ArrayList<>()).add(order);
```

На `ConcurrentHashMap` такие методы особенно полезны, потому что предоставляют атомарные compound-операции на уровне API. При этом mapping function не должна делать тяжёлые или рекурсивно конфликтующие операции без необходимости.

## Что такое fail-fast iterator?

Итераторы обычных коллекций хранят ожидаемую версию структурных изменений и могут бросить `ConcurrentModificationException`, если Map структурно изменилась не через iterator.

Это **best-effort обнаружение ошибки**, а не механизм потокобезопасности.

## Можно ли менять value через Map.Entry во время итерации?

`entry.setValue()` обычно не меняет структуру Map, поэтому допустим. Добавление/удаление keys — structural modification и может нарушить fail-fast итератор.

## Почему capacity делают степенью двойки?

Это позволяет быстро выбирать bucket через битовую маску и эффективно перераспределять entries при удвоении таблицы. Хорошее смешивание хэша особенно важно, потому что индекс зависит от ограниченного числа младших битов.

## Какие методы Map полезно знать кроме put/get/remove?

- `putIfAbsent` — добавить, только если ключ отсутствует;
- `computeIfAbsent` / `computeIfPresent` — вычислить mapping по условию;
- `compute` — пересчитать mapping;
- `merge` — удобно агрегировать значения;
- `getOrDefault` — вернуть default без ручного if;
- `replaceAll` — преобразовать values.

## Типичные ошибки на интервью

- «hashCode определяет уникальность» — нет, окончательное равенство определяет `equals()`.
- «HashMap всегда O(1)» — нет, это average case.
- «resize начинается, когда закончились bucket» — нет, ориентир — threshold.
- «после 8 элементов всегда дерево» — нет, важна общая capacity.
- «LinkedList всегда быстрее ArrayList при вставке» — не если сначала надо O(n) найти позицию.
- «HashMap можно читать/писать из разных потоков, если ошибок пока не было» — это отсутствие гарантии, а не корректность.
