# Деплой и инфраструктура

Раздел собран вокруг вопросов о CI/CD, Docker и поддержке сервиса в продакшене.

## 1. Что такое CI/CD?

CI/CD — набор практик и инструментов, которые автоматизируют проверку, сборку и доставку приложения. **Continuous Integration** означает, что изменения разработчиков регулярно попадают в общую ветку и автоматически проходят сборку и тесты. **Continuous Delivery / Deployment** продолжает этот процесс: готовый артефакт доставляется в окружение или автоматически разворачивается в нём.

Типичная цепочка выглядит так: разработчик делает commit → CI-система забирает код → собирает проект → запускает тесты и проверки → создаёт артефакт или Docker image → помещает его в registry → выполняет deploy на нужное окружение. Главное преимущество — повторяемость процесса и снижение количества ручных ошибок.

## 2. Как работает Docker и из чего состоит Docker image?

Docker позволяет запускать приложение в изолированном контейнере вместе с нужным окружением. Image — неизменяемый шаблон, из которого создаются контейнеры. Он состоит из последовательности слоёв. Каждый слой обычно соответствует инструкции Dockerfile: например, базовому образу, копированию файлов или установке зависимостей.

При запуске image Docker добавляет поверх его read-only слоёв записываемый слой контейнера. Поэтому несколько контейнеров могут использовать общие слои одного image, не дублируя их на диске.

## 3. Что такое слой Docker image и как создаётся новый слой?

Слой — результат файловых изменений, созданных одной инструкцией Dockerfile. Например, `RUN`, `COPY` и `ADD` обычно создают новый слой. Слои кэшируются, поэтому порядок инструкций важен: редко меняющиеся шаги выгодно размещать раньше, а часто меняющиеся — позже.

Если изменился один слой, Docker пересобирает его и все следующие слои, но может повторно использовать предыдущие из cache.

## 4. Что такое Docker Compose?

Docker Compose позволяет описать несколько связанных контейнеров в одном YAML-файле: приложение, PostgreSQL, Redis, Kafka и другие сервисы. В конфигурации задаются images или Dockerfile, переменные окружения, сети, volumes, порты и зависимости между сервисами.

Командой `docker compose up` можно поднять весь набор сервисов как единое окружение. Это особенно удобно для локальной разработки и интеграционных стендов.

## 5. Чем ARG отличается от ENV в Docker?

`ARG` задаёт параметр, доступный во время сборки image. Его можно передать через `--build-arg`. После сборки такой параметр не обязан существовать в окружении контейнера.

`ENV` задаёт переменную окружения, которая сохраняется в image и доступна приложению при запуске контейнера. Поэтому `ARG` обычно используют для параметров сборки, а `ENV` — для настроек runtime. Секреты не стоит бездумно хранить ни в `ARG`, ни в `ENV`, потому что они могут попасть в историю image или метаданные.

## 6. Чем CMD отличается от ENTRYPOINT?

`ENTRYPOINT` задаёт основную команду контейнера — то, что контейнер должен запускать как исполняемую программу. `CMD` задаёт команду по умолчанию либо аргументы для `ENTRYPOINT`.

Например, если `ENTRYPOINT` содержит запуск `java -jar app.jar`, то `CMD` можно использовать для аргументов приложения. Значение `CMD` легко заменить при `docker run`; `ENTRYPOINT` обычно изменяют реже.

## 7. Чем контейнеризация отличается от виртуализации?

Виртуальная машина эмулирует отдельную машину с собственной гостевой ОС. Контейнер использует ядро хостовой ОС и изолирует процессы через механизмы ядра. Поэтому контейнеры обычно запускаются быстрее и требуют меньше ресурсов.

При этом контейнер — не «лёгкая виртуальная машина»: модель изоляции и границы безопасности у него другие. Контейнеры особенно удобны для упаковки и одинакового запуска приложений на разных окружениях.

## 8. Как поддерживать сервис в production и мониторить его работу?

Обычно контролируют технические и бизнес-метрики: latency, RPS, процент ошибок, загрузку CPU и памяти, количество активных соединений, состояние пулов, lag брокеров, время ответов внешних систем. Кроме метрик нужны структурированные логи и трассировка запросов между сервисами.

Важная часть эксплуатации — health checks, alerts и понятные dashboards. Алерты должны сигнализировать не о любом изменении метрики, а о состоянии, которое действительно требует реакции. При инциденте разработчик должен иметь возможность быстро сопоставить метрики, логи и trace конкретного запроса.
