# Object, equals() и hashCode()

::: tip Приоритет
🔴 **Обязательно знать.** Тема почти всегда связывается с `HashMap` и `HashSet`.
:::

## Чем == отличается от equals()?

### Короткий ответ
Для примитивов `==` сравнивает значения. Для ссылок `==` проверяет, указывают ли две ссылки на один объект. `equals()` предназначен для логического равенства и может быть переопределён.

```java
String a = new String("java");
String b = new String("java");

a == b;      // false
a.equals(b); // true
```

## Контракт equals()

### Короткий ответ
Рефлексивность, симметричность, транзитивность, согласованность при неизменном состоянии и `false` при сравнении с `null`.

### Почему это важно
Нарушение контракта может сломать поиск и уникальность в коллекциях. Особенно опасны странные реализации в иерархиях наследования.

## Контракт hashCode()

### Короткий ответ
Если `a.equals(b) == true`, то `a.hashCode()` и `b.hashCode()` обязаны быть одинаковыми. Обратное неверно: одинаковый hashCode разрешён у разных объектов.

## Что будет, если переопределить equals(), но не hashCode()?

### Короткий ответ
Два логически равных объекта могут попасть в разные бакеты HashMap/HashSet, и коллекция перестанет вести себя согласно ожиданиям.

## Должен ли hashCode быть уникальным?

### Короткий ответ
Нет. Диапазон `int` конечен, а объектов может быть больше. Коллизии допустимы, задача hashCode — хорошо распределять объекты.

## Можно ли всегда возвращать 1 из hashCode()?

### Короткий ответ
Функционально контракт можно соблюсти, но все keys попадут в один участок хэш-таблицы и производительность резко ухудшится.

## Почему mutable key опасен?

### Короткий ответ
Если после `put()` изменить поле key, участвующее в `hashCode()/equals()`, key физически останется в бакете, выбранном по старому состоянию, и `get()` может его больше не найти.

## Почему String хороший key?

### Короткий ответ
String immutable и корректно реализует `equals()/hashCode()`, поэтому логическая идентичность ключа не меняется после помещения в map.

## Какие методы Object чаще всего вспоминают?

`equals`, `hashCode`, `toString`, `getClass`, `clone`, `wait`, `notify`, `notifyAll`. На практике важнее уверенно объяснить первые четыре и связь `wait/notify` с monitor.

## Углубление для собеседования

### Какие свойства обязан выполнять equals()?

`equals()` должен быть рефлексивным, симметричным, транзитивным, согласованным и возвращать `false` для `null`. Главное практическое следствие: объект не должен внезапно менять результат сравнения, пока поля, участвующие в equality, не изменились.

### Как связан hashCode() с equals()?

Если `a.equals(b) == true`, то `a.hashCode()` и `b.hashCode()` **обязаны** быть одинаковыми. Обратное неверно: одинаковый hashCode допустим для неравных объектов — это коллизия.

### Что будет, если переопределить equals(), но забыть hashCode()?

В `HashMap`/`HashSet` логически равные объекты могут попасть в разные bucket. В итоге Set может хранить «дубликаты», а Map не находить значение по эквивалентному ключу.

### Какие поля включать в equals/hashCode?

Поля, задающие логическую идентичность объекта. Нежелательно использовать изменяемые поля у объекта, который служит ключом HashMap. Для JPA Entity есть отдельные нюансы: id может появиться только после persist, а proxy влияет на сравнение классов.

### Почему Objects.equals() удобен?

Он корректно обрабатывает `null`: два null равны, один null — не равен ненулевому объекту, иначе вызывается `equals()` первого объекта. Это уменьшает количество ручных null-checks.

### == и equals() — в чём точная разница?

Для примитивов `==` сравнивает значения. Для ссылочных типов `==` сравнивает идентичность ссылок — указывают ли они на тот же объект. `equals()` может быть переопределён и сравнивать логическое состояние.

### Может ли hashCode меняться?

Технически да, если он зависит от mutable fields. Но для объекта, лежащего ключом в hash-based collection, это ломает lookup. Поэтому hashCode ключа должен оставаться стабильным на время нахождения в коллекции.
